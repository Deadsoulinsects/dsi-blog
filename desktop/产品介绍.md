# DSI Admin：从 Obsidian 笔记到博客发布

DSI Admin 面向已有 Astro 博客与 Obsidian 笔记库的作者，把原本需要逐条执行的本地准备步骤放进一个桌面程序。

它目前服务于 DSI-blog 的内容结构与媒体协议，不是适配任意博客平台的通用 CMS。正式网站仍是静态网站，不增加线上管理后端。

## 一篇文章的工作流

```text
选择笔记或目录
→ 本地草稿与元数据
→ 引用解析和附件定位
→ 网页媒体准备与共享渲染
→ 隔离检查和构建
→ 查看差异并确认本地提交
→ 查看所有待推送提交并确认发布
→ 核对对应版本的 Actions 与站点内容索引
```

正文只有一个来源：Obsidian。程序保留原始附件，生成适合网页的派生文件；正文和附件不因准备就被上传。标题和专题修改不应改变既有文章地址。

笔记留在作者原来的目录里，在 Admin 中选择公开内容，不再为发布复制到“博客发布”。默认目录与待确认扫描排除历史“博客发布”副本和 `picture`，来源目录与网站专题可以不同。

已有文章迁移到原笔记需要作者明确重新绑定。候选按文件名或标题比较，忽略大小写、Unicode 表示与空白差异，且排除历史副本；单一候选也不自动绑定，不自动替换已有路径。旧绑定在确认迁移前继续工作，新导入遇到可能重名或同标题的已有文章则提示显式绑定，不另建文章。

重新绑定保留站点文件名、URL、`mediaId` 和其他技术字段。原笔记与发布副本可能各有修改，作者应先比较、整理并选择原笔记内容；程序不会借迁移覆盖笔记或删除私人副本。

博客日期以源笔记的 `completion_date` 为准；缺失时提示补齐，不推断为当天。源笔记明确提供的作者元信息随同步更新，站点技术字段保留；标签与可选起止日期可传入正式站。Obsidian 插件生成的受管头部是派生内容，导入时去除重复，再由站点独立渲染。

## 管理与阅读

目录导入形成专题层级，父专题包含后代文章，支持整目录选择和单篇排除。专题导航与文章列表位于上方，当前文章的编辑、检查和预览位于下方全宽面板。板块可折叠，任务结果用文章和阶段说明，不要求作者理解内部 UUID 或终端字段。

正文预览复用正式网站的内容规则与阅读样式，包括图库、图片和视频；它不是另一套 Markdown 编辑器，也不把准备结果冒充正式上线。

多篇文章可作为一批准备：在一个隔离工程中整理正文、元信息、链接和媒体，共享附件转换结果，整批检查和构建一次。逐篇问题仍能定位；单篇整理失败不阻止其他文章进入检查，整批工程检查失败则不会误标为准备就绪。

就绪文章打开提交面板时复用当前版本的检查结果，不再重复准备和构建。提交前仍核对原文、附件、草稿与工程是否变化，并检查所选文章的引用闭包和媒体预算；结果失效时先重新准备。

站点结构视图用于检查本地专题与文章路由，帮助发现路径冲突、来源问题和分类问题。未提交草稿与正式版本仍需区分。

专题描述可在 Admin 中按完整路径编辑，父专题与子专题互不覆盖；保存为本地草稿，清空可移除介绍。描述可单独或随文章确认差异后提交到站点配置，不改原笔记、文章归属或地址，也不触发文章重新准备。公开专题页在后续构建发布时使用已提交的描述。

文章页专题区最多展示两个一级专题。作者在 Admin 选择一个置顶专题作为第一位，其余按专题内最新文章完成日期自动补位并去重，后代文章也参与日期判断。未置顶或置顶没有文章时按最近顺序展示，专题不足不保留空白位置。置顶与描述共用本地草稿、差异确认、冲突保护和配置提交，不触发文章准备。

## 操作边界

本地保存和准备不修改正式仓库；用户确认提交才写入精确文件闭包。提交信息由作者填写，已有无关暂存内容不会被夹带或清除。

发布包含所有已提交未推送的版本，采用非强制 Git push；工作目录里的未提交编辑不进入发布构建。部署成功必须匹配此次 commit 的 SHA，不能凭“传输完成”判断。

程序以普通 Windows 用户运行，界面通过受限接口调用本地引擎。安装目录与仓库、笔记库分离；配置、草稿和日志留在安装目录 data 中。升级保留数据，关闭协调自动保存和后台任务，恢复时不重复提交或推送。

## 发布范围

当前提供 Windows x64 安装程序；其他平台未承诺兼容。安装包体积包含完整 Electron、Git、媒体转换与工程检查工具，换取不依赖用户全局 Node、FFmpeg 和手动开发服务。

原笔记选择与迁移是本轮未发布的源码变化，没有重建安装包或修改安装数据；安装版需要后续打包升级。博客同步已退出根目录 `prebuild`，起源同步与其他准备步骤保留。单篇手动同步仍可显式使用 `npm run sync:blog -- --file "<原笔记路径>"`，加 `--dry-run` 预览；不指定文件只输出说明，不扫描旧目录。

真实 GitHub 发布需要网络、仓库权限、正确的站点地址与匹配的部署 workflow。公开发布资料应包含 README、版本更新记录、许可证和对应版本的验收证据。
