# 文档信息架构

本文档是项目文档地图，用来定义这套文档要解决什么问题、分别写给谁看，以及每份文档各自负责什么，不负责什么。

## 文档边界总原则

本项目的文档分成两层：

1. 根目录 `docs/` 里的文档，面向维护者与 AI 协作者，负责项目维护、结构说明、操作流程与内部约束。
2. `src/content/docs/` 里的文档，面向站点访客，负责公开可浏览的教程、说明与使用型内容。

这两层不要混写。

- maintainer / AI 文档只放在根目录 `docs/`
- visitor-facing 文档只放在 `src/content/docs/`
- `src/content/docs/intro.md` 是访客入口文档，不是维护手册，不承担内部操作说明职责

## 本轮锁定的目标文档集合

当前批准维护的文档文件集只有以下 6 个：

1. `README.md`
2. `docs/README.md`
3. `docs/project-structure.md`
4. `docs/maintenance-quickstart.md`
5. `docs/operations-workflow.md`
6. `升级优化规划.md`

在这一轮文档重构中，不额外扩展新的根目录说明文档，不把职责拆散到更多文件里。

## 公开文档与内部文档的分界线

### 根目录 `docs/`

这里是维护文档区。

适合放：

- 仓库结构说明
- 维护上手说明
- 操作流程边界
- AI 协作时需要遵守的内部文档分工

不适合放：

- 面向普通访客的站内介绍
- 作为网站内容发布的教程正文
- 代替 `src/content/docs/` 出现在公开站点中的内容

### `src/content/docs/`

这里是公开文档区。

适合放：

- 访客可阅读的教程
- 使用说明
- 配置说明
- 对外公开的稳定文档内容

不适合放：

- 维护者内部流程
- 仓库治理规则
- AI 执行约束
- 发布前检查责任分工

## 使用规则

当一条信息需要写入文档时，先判断它回答的是哪一类问题：

- 如果它回答“这个仓库整体是什么、怎么开始看”，优先写到 `README.md`
- 如果它回答“整套文档怎么分工、哪份文档才算准”，写到 `docs/README.md`
- 如果它回答“某个目录或文件夹负责什么”，写到 `docs/project-structure.md`
- 如果它回答“日常维护最短应该怎么走”，写到 `docs/maintenance-quickstart.md`
- 如果它回答“完整操作流程与责任边界是什么”，写到 `docs/operations-workflow.md`
- 如果它回答“以后要怎么升级、为什么暂时不做”，写到 `升级优化规划.md`

如果内容是给站点访客直接阅读的，则不要写进根目录 `docs/`，应放到 `src/content/docs/`。
